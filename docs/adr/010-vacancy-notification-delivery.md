# ADR-010 빈자리 알림 발송: 매칭 → RabbitMQ → Redis Pub/Sub → SSE

- 상태: 승인

## 맥락

- 사용자는 자주 가는 충전소를 골라 두고, 그곳에 자리가 나면 바로 알고 싶다.
- 빈자리 이벤트(`charger.available`)는 최소 한 번 전달되므로 같은 이벤트가 다시 올 수 있다(ADR-004).
- 사용자별 발송은 따로 성공·실패하고, 실패한 것만 다시 시도해야 한다(ADR-008).
- 로그인 기능이 없다. 앱 인스턴스가 여러 대일 수 있고, 구독자는 그중 아무 인스턴스에나 실시간 연결(SSE)을 맺는다.

## 결정

```
charger.available ─▶ 매칭(Kafka 소비자) ─▶ notification_log PENDING ─▶ RabbitMQ 발송 작업 ─▶ 발송기
                                                                                    │
                    구독자의 SSE 연결 ◀── 인스턴스마다 전달 ◀── Redis Pub/Sub ◀────┘
```

| 단계 | 하는 일 | 실패하면 |
|---|---|---|
| 구독 | 브라우저가 만든 무작위 값(`X-Client-Key`, UUID)으로 구독자를 구분한다. 한 구독자는 충전소 20곳까지 | - |
| 매칭 | 빈자리 이벤트의 충전소를 구독 중이고 쿨다운(10분)이 지난 구독마다 발송 기록(PENDING)을 만들고, 마지막 알림 시각을 바꾼다. 한 SQL 문이라 원자적이다 | Kafka가 같은 이벤트를 다시 준다 |
| 적재 | PENDING 기록을 500건씩 RabbitMQ에 넣고 **브로커 확인(publisher confirm)** 을 기다린 뒤 QUEUED로 표시한다. 다 넣으면 오프셋을 커밋한다 | Kafka 재처리 때 기록은 새로 생기지 않고(유니크 제약) 남은 PENDING만 다시 넣는다 |
| 발송 | 그 사이 구독을 해지했으면 CANCELLED로 두고 보내지 않는다. 이미 SENT면 건너뛴다. 시도 횟수를 올리고 Redis Pub/Sub에 올린 뒤 SENT로 표시한다 | 1초, 2초 뒤 다시 시도해 모두 3번. 끝내 실패하면 FAILED로 기록하고 DLQ로 보낸다 |
| 전달 | 모든 인스턴스가 채널을 구독하다가, 자기에게 연결된 그 구독자의 SSE 연결에 `notification` 이벤트로 보낸다. 전달은 크기가 정해진 스레드 풀(4개)에서 한다 | 연결이 없으면 실시간 전달은 사라지고 알림함(`GET /api/notifications`)에서 본다 |

- **쿨다운 기준은 이벤트 발생 시각이다.** 처리 시각을 쓰면 같은 이벤트를 다시 처리할 때 결과가 달라진다. 발생 시각을 쓰면 재처리해도 같은 판단이 나온다.
- **같은 충전소의 이벤트는 같은 파티션에서 차례로 처리된다**(키 = 충전소 ID). 그래서 한 구독의 쿨다운 판단이 동시에 엇갈리지 않는다.
- **상태는 되돌리지 않는다.** 모든 상태 변경은 "아직 SENT·CANCELLED가 아닐 때만" 적용한다. 적재 확인보다 발송이 먼저 끝나도 QUEUED가 SENT를 덮지 않는다.
- **거르는 이벤트:** 시연용 상태(`source=MANUAL`)는 개발 도구를 켠 환경에서만 알린다. 시연 알림은 몇 번이고 확인할 수 있게 쿨다운을 적용하지 않고, 실제 알림의 쿨다운 기준(마지막 알림 시각)도 바꾸지 않는다. 15분이 지난 빈자리는 알리지 않는다(장애 뒤 밀린 이벤트, 첫 배포 때 토픽에 남은 과거 기록).
- **clientKey는 화면으로 보내지 않는다.** Redis 메시지에는 받을 연결을 고르려고 넣지만, SSE로 보내는 알림 본문에서는 뺀다. `EventSource`는 헤더를 붙일 수 없어 SSE 연결만 쿼리 파라미터로 받는다. 쿼리 문자열은 프록시·로드 밸런서의 접근 로그에 남을 수 있으므로, 운영에서는 `/api/vacancies/stream`의 `clientKey`를 로그에서 가려야 한다.

## 검토한 대안

| 대안 | 채택하지 않은 이유 |
|---|---|
| 매칭 후 바로 SSE로 보냄 (RabbitMQ 없이) | 사용자별 재시도와 최종 실패 격리(DLQ)를 직접 만들어야 한다. 매칭(Kafka 파티션)과 발송 속도가 묶인다 |
| 발송 기록 없이 큐에만 넣음 | 적재 실패와 재처리 사이에서 작업을 잃거나 두 번 만들 수 있다. 알림함도 만들 수 없다 |
| 트랜잭션 아웃박스 + 별도 릴레이 | 같은 보장을 얻지만 폴링 릴레이가 하나 더 필요하다. 여기서는 Kafka 재처리가 릴레이 역할을 하므로 생략했다 |
| 발송 기록을 RabbitMQ에서만 관리 | "이미 보냈는지"를 메시지만으로는 알 수 없다. DB 기록이 멱등성의 기준이다 |
| 인스턴스 사이 전달을 Kafka 토픽으로 | 가능하지만 인스턴스·재기동마다 컨슈머 그룹이 또 늘어난다. 저장이 필요 없는 짧은 전달이라 Redis Pub/Sub이 맞다 |
| 웹 푸시(Push API, 서비스 워커) | 브라우저를 닫아도 받을 수 있지만 VAPID 키, 구독 저장, 서비스 워커가 필요하다. 다음 단계로 미뤘다 |

## 결과

- 얻은 것: 같은 이벤트가 몇 번 와도 구독자 한 명에게 한 번만 기록된다. 적재·발송 중 어디서 멈춰도 작업을 잃지 않는다(Kafka 재처리, RabbitMQ 재시도).
- 얻은 것: 발송 상태(PENDING → QUEUED → SENT/FAILED/CANCELLED)와 시도 횟수가 DB에 남아 문제를 추적할 수 있다. 지표: `notification.matched`, `notification.queued`, `notification.sent`, `notification.failed`, `notification.cancelled`, `notification.push.dropped`, `notification.events.skipped{reason}`.
- 감수한 것: 해지 확인과 발송 사이의 아주 짧은 순간에 해지하면 알림이 갈 수 있다. 발송이 DB 밖(Redis)에서 일어나 완전히 막을 수 없다.
- 감수한 것: 발송 후 SENT 기록 전에 멈추면 한 번 더 갈 수 있다(최소 한 번). 화면이 `notificationId`로 거른다.
- 감수한 것: 실시간 전달은 화면이 열려 있을 때만 된다. 탭이 가려져 있으면 브라우저 알림(Notification API, 권한 허용 시)을 띄우고, 화면을 닫았으면 알림함에서 본다.
- 감수한 것: 로그인이 없어 clientKey를 아는 사람은 그 구독자의 구독과 알림을 볼 수 있다. 추측하기 어려운 무작위 값이고 개인 정보는 담지 않는다. 다른 기기와 구독을 맞추려면 로그인이 필요하다.
- 감수한 것: 구독자 생성에 인증이나 속도 제한이 없고, 다시 오지 않는 브라우저의 구독도 만료되지 않는다. 한 충전소의 구독이 크게 늘면 이벤트 하나가 그만큼의 기록과 작업을 만든다. 적재를 500건씩 나눠 메모리와 쿼리 크기는 묶었지만, 공개 운영 전에는 IP 기준 속도 제한과 오래 접속하지 않은 구독자의 구독 만료가 필요하다.
- 감수한 것: 큐나 바인딩이 없으면 브로커는 메시지를 버리고도 확인을 준다(mandatory를 쓰지 않음). 큐와 바인딩은 앱이 기동할 때 선언하므로 평소에는 일어나지 않지만, 그때는 기록이 QUEUED로 남는다. 오래 QUEUED·PENDING인 기록을 경보하거나 다시 넣는 작업은 아직 없다.
- 감수한 것: FAILED나 DLQ로 간 작업은 자동으로 다시 보내지 않는다. 원인을 확인한 뒤 DLQ 메시지를 큐로 옮기면 다시 발송된다(SENT가 아닌 기록은 다시 보낼 수 있다).
- 감수한 것: 적재 확인 뒤 QUEUED 표시 전에 멈추고, 재처리 전에 해당 이벤트가 15분을 넘겨도 남은 PENDING은 마저 보낸다. 이미 매칭된 알림이라 늦더라도 보내는 쪽을 택했다.
