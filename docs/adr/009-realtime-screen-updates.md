# ADR-009 검색 화면의 실시간 갱신: 빈자리는 SSE, 나머지는 주기 조회

- 상태: 승인

## 맥락

- 검색 화면은 지도에 보이는 충전소의 사용 가능 대수를 보여 준다. 사용자가 가장 알고 싶은 순간은 "자리가 났다"이다.
- 서버에는 빈자리 이벤트(`charger.available`)가 이미 있다. 반면 "충전대기 → 충전중"(자리가 찬 것) 같은 다른 변화는 이벤트로 발행하지 않고 DB에만 반영된다(ADR-003, 005).
- 원본 상태는 2분마다 수집된다(ADR-001). 그보다 자주 다시 읽어도 새 정보가 거의 없다.

## 결정

| 변화 | 화면 반영 방식 |
|---|---|
| 빈자리 (충전중 → 충전대기) | **Server-Sent Events**로 즉시 받는다. 화면에 있는 충전소면 알림을 띄우고, 그 충전소와 현재 검색 결과를 다시 읽는다 |
| 그 외 변화 | 화면이 **2분마다** 현재 검색과 열려 있는 상세를 다시 읽는다. 탭이 보이지 않으면 건너뛴다 |
| 놓쳤을 수 있는 변화 | 스트림이 다시 연결되거나 탭으로 돌아오면 바로 다시 읽는다 |

서버 쪽 구성은 다음과 같다.

- 인스턴스마다 무작위 컨슈머 그룹으로 `charger.available`을 최신 위치부터 구독한다. 그래서 인스턴스가 여럿이어도 각자 자기에게 연결된 화면에 모든 빈자리를 보낸다.
- 지역별로 거르지 않고 모든 빈자리를 보낸다. 서울 기준 시간당 수백 건이라 부담이 작고, 화면에 있는 충전소만 고르는 일은 클라이언트가 한다.
- 25초마다 주석을 보내 프록시가 유휴 연결을 끊지 않게 한다. 연결은 최대 30분 유지한다.
- 네트워크가 끊기면 `EventSource`가 스스로 다시 연결한다. 서버가 거절(503 등 HTTP 오류)하면 `EventSource`는 다시 연결하지 않으므로, 화면이 30~40초(무작위 간격) 뒤 직접 다시 연결한다.
- 인스턴스당 동시 연결은 500개까지 받고, 넘으면 503과 `Retry-After`로 거절한다. 연결 수는 자리를 먼저 예약해 세므로 동시 요청이 몰려도 상한을 넘지 않는다.
- 같은 빈자리 이벤트가 다시 와도(최소 한 번 전달) 화면은 최근 `eventId`를 기억해 알림을 한 번만 띄운다.
- 앱이 멈출 때는 웹 서버의 graceful shutdown보다 먼저 모든 SSE 연결을 닫는다. 그러지 않으면 열린 연결 때문에 종료가 30초 동안 막힌다.
- 인스턴스마다, 재기동마다 새 컨슈머 그룹(`vacancy-stream-*`)이 생긴다. 쓰지 않는 그룹이 기본 7일간 남으므로 컨슈머 랙 경보에서는 이 그룹(과 `dev-tools-recent-vacancies-*`)을 제외한다.

## 검토한 대안

| 대안 | 채택하지 않은 이유 |
|---|---|
| 주기 조회만 (예: 60초) | 빈자리를 최대 1분 늦게 보여 줌. 서비스의 핵심 순간을 놓침 |
| WebSocket | 서버 → 화면 한 방향이면 충분함. SSE는 HTTP 그대로라 단순하고 자동 재연결이 내장됨 |
| 모든 상태 변화를 SSE로 | 감지기가 상태 변화 이벤트를 따로 발행해야 하고, SNAPSHOT 때 7.6만 건이 화면으로 쏟아질 수 있음 |
| 화면이 보는 영역만 구독 | 서버가 연결마다 영역을 관리해야 함. 지금 규모에서는 이득이 작음 |

## 결과

- 얻은 것: 빈자리는 감지 후 1~2초 안에 화면에 뜬다(로컬 측정). 다른 변화도 최대 2분 안에 맞춰진다.
- 감수한 것: 자리가 찬 변화는 최대 2분 늦게 보인다. 이벤트를 하나 늘리는 대신 이 지연을 받아들였다.
- 감수한 것: 이벤트를 보내는 일은 Kafka 리스너 스레드에서, keep-alive는 별도 스레드 하나에서 한다. 같은 연결로의 전송은 순서대로 처리되므로, 아주 느린 연결이 많아지면 다른 화면으로 가는 전달과 keep-alive가 함께 늦어질 수 있다. 연결 수 상한과 실패한 연결 즉시 정리로 줄였다.
- 감수한 것: 연결 전이나 끊긴 동안의 빈자리는 다시 보내지 않는다. 화면은 처음 연결할 때, 다시 연결될 때, 탭으로 돌아올 때 검색 API로 현재 상태를 읽어 맞춘다.
