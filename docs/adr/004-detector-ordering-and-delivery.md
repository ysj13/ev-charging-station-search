# ADR-004 빈자리 감지의 처리 순서와 전달 보장

- 상태: 승인

## 맥락

감지기는 `charger.status`를 배치로 소비하면서 한 배치마다 네 가지 일을 한다.

- 직전 상태를 읽는다
- 빈자리 이벤트를 발행한다
- DB 상태를 갱신한다
- Redis 상태를 갱신한다

어느 단계에서든 실패할 수 있고, 실패하면 배치 전체가 다시 처리된다. 지켜야 할 목표는 두 가지다.

- 빈자리 이벤트를 **잃지 않는다**
- 같은 이벤트를 **불필요하게 반복 발행하지 않는다**

## 결정

**처리 순서:** 직전 상태 조회(Redis, 없으면 DB) → 전이 감지 → 이벤트 발행 확인 → DB 갱신 → Redis 갱신 → 오프셋 커밋

| 규칙 | 내용 | 이유 |
|---|---|---|
| 순서·중복 판단 | 공공데이터 상태갱신일시가 **직전보다 늦을 때만** 반영. 같으면 무시 | CHANGE/SNAPSHOT 중복과 순서 역전 처리. DB·Redis·전체 동기화가 같은 규칙을 씀 |
| Redis를 마지막에 갱신 | 실패 후 재처리 때 같은 전이를 다시 감지할 수 있음 | 이벤트 유실 방지 |
| 발행한 이벤트 기억 | 최근 발행한 `eventId`를 메모리에 보관하고 재처리 때 건너뜀 | DB 장애가 길어질 때 재시도마다 같은 이벤트가 반복 발행되는 것 방지 |
| 전달 보장 | **최소 한 번(at-least-once)**. `eventId` = `충전소:충전기:상태갱신시각` | 재기동으로 메모리가 비면 다시 나갈 수 있음. 소비자가 `eventId`로 중복을 거름 |
| Redis 대체 | Redis에 직전 상태가 없으면 DB의 현재 상태를 기준으로 삼고, 그 값을 Redis에 저장 | Redis를 잃어도 빈자리를 놓치지 않음 |
| 오래된 빈자리 | 15분보다 오래전에 일어난 빈자리는 상태만 반영하고 이벤트는 발행하지 않음 | 첫 배포 시 토픽의 과거 기록이나 장애 뒤 밀린 메시지로 지난 알림이 쏟아지는 것 방지 |
| Redis 쓰기 | Lua 스크립트로 "저장된 값보다 최신일 때만" 원자적으로 덮어씀 | 컨슈머 재조정으로 잠시 두 곳에서 처리해도 상태가 과거로 돌아가지 않음 |
| 오류 처리 | 인프라 오류는 1초~1분 간격으로 멈추지 않고 재시도. 역직렬화할 수 없는 메시지는 건너뜀 | 메시지를 버리면 이벤트를 영영 잃음. 재시도는 원인을 담은 WARN 로그와 지표 `kafka.listener.retries`로 드러냄 |

## 검토한 대안

| 대안 | 채택하지 않은 이유 |
|---|---|
| DB 갱신 → 발행 순서 | Redis가 없어 DB를 기준으로 삼을 때, 발행이 실패한 뒤 재처리하면 DB가 이미 새 상태라 전이를 놓침 |
| Kafka 트랜잭션으로 exactly-once | Redis·DB가 트랜잭션 밖이라 전체를 정확히 한 번으로 묶을 수 없음. 비용만 늘어남 |
| 일정 횟수 실패 후 메시지 버리기(DLT) | 대부분 일시적인 인프라 장애라 버리면 이벤트 유실. 막힌 파티션은 지표와 컨슈머 랙으로 감지 |

## 결과

- 얻은 것: 장애가 있어도 빈자리 이벤트를 잃지 않는다. 같은 이벤트의 반복 발행도 대부분 막힌다. 장애 주입 테스트로 "DB 1회 실패 → 재처리 → 이벤트 1건"을 확인했다.
- 감수한 것: 소비자는 `eventId`로 중복을 걸러야 한다. 처리할 수 없는 메시지가 생기면 해당 파티션이 막히므로 컨슈머 랙 경보가 필요하다.
- 15분 기준이 실제 지연 분포에 맞는지는 지표 `detector.status.lag`(p50·p90·p99)로 확인해 조정한다.
